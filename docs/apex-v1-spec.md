# Apex 高光录制器 · v1 设计定稿

> 状态：设计已定稿，检测链路已用真实素材验证；采集器第一段（实时检测）可跑。
> 日期：2026-10-27　｜　素材：`D:\played\probe\s_20261027_202202`（2560×1440，352s，715 帧，48kHz 立体声）

## 0. 一句话

**WGC 抓窗口 → 常驻环形缓冲 → 画面里那块 "KNOCKED DOWN" banner 触发 → 往前回取固定前摇 → 落盘成片 → 本地回顾库。**

不做注入、不读内存、不走 Overwolf GEP、不做 OCR、不靠音频判定。

## 0.1 项目约束（不可谈判）

这些是用户定过的，写进文档是为了不再被我自己弄丢：

| 约束 | 内容 | 理由 |
|---|---|---|
| **开源** | MIT，代码在 GitHub 公开 | 用户的核心目标就是做成开源项目 |
| **无账号 / 无服务器** | 不登录、不上传、不联网 | 录制文件在本地；没有后端就没有运维和隐私问题 |
| **分发形态** | GitHub Releases 下载即用，**单个 self-contained exe**（约 70MB，自带 .NET 运行时，目标机无需预装任何东西） | 开源项目的第一次运行成本是生死线 |
| **不注入** | 不 DLL 注入、不读内存、不装驱动、不模拟输入 | 反作弊风险 + 可移植性 |
| **禁止把 OBS 拖进来当引擎** | 见 §0.2 | GPL 传染 + 300MB 依赖 + 「先装 OBS」的首次体验 |

## 0.2 为什么不用 OBS 当录制引擎（评估过，结论是不用）

OBS 能免费给：WGC 采集、NVENC、可配置长度的重放缓冲、无损封盘、多轨音频、崩溃恢复。
OBS 给不了或代价太大：

1. **GPL 传染**：做 OBS 插件 = 衍生作品 = 必须 GPL-2.0，和 MIT 冲突；即便只走 obs-websocket 隔离，也把项目从「一个工具」降级成「OBS 的附属脚本」。
2. **分发形态崩了**：「先装 300MB 的 OBS 再开我们」对开源项目是致命的首次成本。
3. **不能合并/精确裁剪**：同一场交火两次击倒会产出两份重叠文件，还得调 ffmpeg 再剪；自研环形缓冲在内存里就能拼成一条。
4. **缓冲长度不能热改**：改前摇要停缓冲、改配置、重启，中间丢一段。

**保留为可选的未来后端**：等 v1 自研链路稳定后，若有人想用 OBS 生态，再单写一个 `IObsBackend` 适配器（约 300 行，走 obs-websocket）。它不是 v1 的一部分。

## 1. 验证结论（这些是定稿的依据）

### 1.1 已证实

| 项 | 结果 |
|---|---|
| WGC 能抓 Apex | 8s 内 482 帧（≈60fps），亮度 min 0 / max 255 / avg 72 |
| banner 模板匹配能杀干净 | 4 次击倒全部命中，**零误报**；分数 **0.98 / 0.94 / 0.95 / 0.95**，事件外最高分 **0.392**（模板换 260×40 + 条带扩到 640 后重测） |
| banner 持续时长 | ≥2s（2fps 采样下 5 帧连续），足够 10fps 采样抓到 |
| 时序 | **声音在前、banner 约晚 0.5s** |

### 1.2 已证伪（不要再试）

- **能量/峰值触发**：整段 rms p50 = −18.7 dBFS、peak p50 = −9.1、p99 = 0.0 —— 永远贴着满电平，没有动态余量，击倒点的电平与随便一秒无区别。
- **谱通量（自适应白化）**：击倒点 ±0.45s 没有峰，最强帧与标签无关。
- **log-mel 音频指纹**：两次击倒之间互相 NCC = **+0.171**，而随机窗口对模板平均 **+0.383** —— 两次真实击倒的相关性比它们和随机噪声的还低。
- **粗粒视觉特征**：ROI 白像素数/边缘能量被 HUD 淹没（击倒帧排名 277/715）。

### 1.3 由验证结果直接删掉的设计

- 音频指纹触发器（整段删）
- OCR / 读伤害数字（整段删，模板匹配不读字）
- 「视觉钓鱼」模板冷启动 + 「3 次转正 / 20 次淘汰」的模板晋升机制（整段作废：模板是自带的，不是学来的）

## 2. 架构

```
[采集] WGC(CreateFreeThreaded) ──► D3D11 纹理 ──► NVENC/H.264 ──► fMP4 1s 分片 ──► 磁盘环
                                        └──► 条带(1280×120@2560 基准) ──► [检测] NCC
                                                                          │ score ≥ 0.60
                                                                          ▼
[切分] 前摇 P + 后摇 5s ──► 合并 ──► 截断 ──► [库] 文件名=时间戳+暗号，索引=sqlite/json
```

采集与检测**同一帧源**：检测在采集线程里跑，只读条带，不复制整帧。

## 2.5 配置驱动（多游戏 / 社区扩展）

检测器不认识“Apex”，只认识**一份 JSON + 若干张模板图**：

```json
{
  "id": "apex", "name": "Apex Legends",
  "windowTitles": ["Apex Legends"],
  "refWidth": 2560, "refHeight": 1440,
  "band": { "x": 640, "y": 1000, "w": 1280, "h": 120 },
  "minGapMs": 500, "preRollSec": 30, "postRollSec": 5,
  "templates": [
    { "id": "knock", "label": "击倒", "file": "apex/knock.png", "threshold": 0.60 }
  ]
}
```

- **坐标一律以 `refWidth×refHeight` 为基准**，运行时按实际窗口尺寸等比缩放 → 同一份配置跑 1080p/1440p/4K。
- **模板是 PNG**（灰度/彩色都行，内部转亮度 + 高通），社区贡献门槛是“截一张图、裁一条、存成 png”。
- 多模板：每个模板独立阈值，取全场最高分；标签随命中模板走（将来 `assist.png` 可以标“助攻”）。
- 配置文件查找顺序：显式路径 → **数据目录 `games/`** → `./games/<id>.json` → 从 exe 目录逐级向上找 `games/<id>.json`（最多 8 级）。
- 内置配置以 `EmbeddedResource` 形式编进 exe（`LogicalName="games/%(RecursiveDir)%(Filename)%(Extension)"`），首次启动由 `Paths.EnsureGames()` 释放到数据目录；**目标文件已存在就跳过**，所以用户改过的配置不会被升级覆盖。
- 新增一款游戏 = 新增一个 `games/<id>.json` + 一张模板图，**不改代码**。

## 3. 触发器参数

| 参数 | 值 | 说明 |
|---|---|---|
| 取景条带 | x 640–1920, y 1000–1120（2560×1440 基准） | 按 `W/2560`、`H/1440` 缩放后双线性归一到 1280×120；左扩到 640 是为了容纳 `ASSIST, ` 前缀 |
| 模板 | 305×44 灰度，取自 `f_00202557` 的 (980,1030) | `D:\played\probe\template.bin`（int32 w、int32 h、灰度） |
| 预处理 | 高通 = 原图 − 25×25 均值（边缘复制填充），模板去均值 | |
| 打分 | NCC = corr /(n·sd·std(tpl))，窗口 sd ≤ 3 记 0 | |
| 触发阈值 | **0.70**（用户可在托盘菜单/回顾库里自己调，见 §3.5） | 2026-10-28 真机一局核对：6 次真击倒落在 0.69–0.98，2 次误判在 0.626/0.630（同一处画面 1 秒内重复触发，两块补丁相关 0.979）。0.65 刚好能挡，但最低真命中 0.694 离它太近，故取 0.70 |
| 采样率 | **10fps**（100ms 一帧） | banner 持续 ≥2s，10fps 稳抓 20 次 |
| 去重 | **上升沿触发**：分数 ≥0.60 且上一帧 <0.60 才算新事件，两次事件最小间隔 500ms | 固定 3s 冷却会吞掉交火中连续的击倒（第二局 2 次自击倒只抓到 1 次的头号嫌疑） |
| 搜索 | 粗扫 step 4 取前 3，再 ±5 内 step 1 细化 | 比全图 FFT 便宜一个量级 |
| 语言 | 简中 / 繁中 / EN 各一份模板 | 模板对语言敏感，但**不敏感于名字**（高通后只剩字形） |
| 分辨率鲁棒 | 条带归一化 + 多尺度 0.85 / 1.0 / 1.15 | v1 只实测 2560×1440 |
| 健康度 | 连续 20 局零命中 → 提示「模板可能失效」 | UI 改版兜底 |

**性能**：1280×120 条带 **6.5–9.5 ms/帧**（原生路径，C# SIMD，实测 9.5 ms）；10fps 下 ≈ 10% 单核。

**诊断开关**：`live.log.csv` 逐帧记录 `t_ms,score,x,y`；`near_*.bmp` 保存分数落在 `[当前阈值-0.15, 当前阈值)` 的条带（每次 ≥2s 一条，上限 40 个），用于事后判断“漏检是因为没到阈值、还是横幅压根没出现”。近失阈值跟着命中阈值走：阈值调到 0.90 时还按 0.45 采样会存一堆没用的图，调到 0.55 时 0.45 又太低。

### 3.5 检测灵敏度可自调（2026-10-28 已实现）

阈值不是「设好了就别动」的常数——不同显示器、不同 UI 缩放、不同地图背景都会让它需要微调。所以做成用户可以直接点的一项：

| 项 | 值 |
|---|---|
| 默认值 | **0.70** |
| 存储 | 数据目录下 `config.json` 的 `Threshold` 字段（和配额同一文件） |
| 0 的含义 | **按模板自带**（即 `games/<id>.json` 里该模板的 `threshold`），不覆盖 |
| 档位 | 0.55 / 0.60 / 0.65 / 0.70 / 0.75 / 0.80 / 0.85 / 0.90，每档带人话标签（宽松 / 推荐 / 偏严 / 很严） |
| 入口 ① | 托盘右键 →「检测灵敏度（0.70）」→ 选档 |
| 入口 ② | 回顾库工具栏 →「灵敏度」下拉 |
| 入口 ③ | 命令行 `--threshold=0.75`（调试/回归用） |
| 生效 | **立即**，不用重启、不用重开录制、不重建编码器 |
| 回归工具 | `--band-check --dir=<含 hit_*.bmp 的目录> --threshold=0.60,0.65,0.70,0.75` |

**为什么用固定档位而不是滑块**：用户要一眼看出「0.70 是推荐值」这种语义，无刻度滑块只会让人瞎拖。

**为什么三个入口共享一份存储**：托盘改了，正开着的回顾库下拉会跟着变；在回顾库里改了，托盘菜单文字也跟着变。实现上只有一个写入口（`TrayApp.ApplyThreshold`），库窗口只发回调。

**写盘只改一个字段**：`DetectPolicy.Save` 用 `JsonObject` 读出原文件、只覆写 `Threshold`，配额那几项原样保留——整体重写会把用户手改过的注释/字段顺序/未知字段全冲掉。

**调阈值之后怎么自证没调坏**：录制时命中/近失都会把条带存成 `captures/hit_*.bmp`、`near_*.bmp`，文件名里带当时分数。`--band-check` 把这些图重跑一遍检测器，输出每个阈值下「命中几张 / 挡掉几张 / 挡掉的是谁」。2026-10-28 的回归数据：

| 阈值 | 命中 | 挡掉 |
|---|---|---|
| 0.60 | 9 张 | 3 张（全是 near_*，本来就该挡） |
| 0.65 | 7 张 | 5 张（+ hit_00876 0.609、hit_00877 0.633 两次误判） |
| 0.70 | 7 张 | 5 张（同上） |
| 0.75 | 7 张 | 5 张（同上） |

即 0.65–0.75 之间结果完全一致，都不误杀真命中（最低真命中 0.694），选 0.70 取中间留双向余量。

## 4. 片段参数

| 参数 | 值 |
|---|---|
| 前摇 P | **{15s, 30s, 60s}，默认 30s**（用户可调） |
| 后摇 | 5s（**必须等环形录满才落盘**，见下方坑） |
| 合并窗口 | 相邻击倒间隔 ≤ 8s 合并为一段 |
| 时长上限 | **P + 35s**（自适应：单次交火最多看 35s） |
| 「更长」 | 封顶 60s，不做无限 |
| 超限策略 | 从**前面**截断，保留尾部（结尾是决定胜负的那几下） |
| 环形缓冲 | 最大前摇 + 后摇 + 检测延迟 + 10s → 60s 前摇时 **90s**（1440p/20Mbps ≈ 225MB 磁盘） |

> 环形长度必须按**最大可配前摇**算。改配置时先扩环形、再放宽上限，否则用户拉滑杆那一刻过去 30s 已经被覆盖了。

> **后摇的坑（2026-10-28 修）**：命中那一刻环形只写到命中时刻，`coverTo == hitMs`，直接切会把后摇夹成 0 —— 实测 24s 命中出片只有 23.5s。现在命中只**登记**到 `_pending` 队列，由独立的 "clip" 线程等到 `coverTo >= hitMs + postRollSec` 再切；`Dispose` 时 `FlushPending()` 兜底把没等满的也切掉（前摇画面不能白丢）。

### 4.5 环形缓冲形态（已定）

- **v1 用 (a) 分片文件环**：每段 fMP4 落成一个文件，保留最近 N 段，删最旧。理由：能看见、能验证、崩了也有文件，而 v1 的首要目标是把链路跑通。
- **跑稳后迁移到 (c) 预分配单文件环**：一个 225MB 预分配文件 + 环形写指针，无碎片、可恢复、不吃内存。
- **迁移契约**：环形缓冲只暴露 `Append(pts, au, isKey) -> SegmentId` / `Read(SegmentId)` / `Trim(keepSeconds)` 三个方法，上层（切片段、写库）只认 SegmentId，不碰文件路径。换形态 = 换实现，不动上层。
- 这条路线是用户 2026-10-27 明确要求记住的。

## 5. 存储

- 编码：H.264（NVENC 优先），**1s fMP4 分片**，keyint 1s
- **GOP 的正确设法定案（踩了一整天）**：NVENC MFT 只认 `ICodecAPI::SetValue(CODECAPI_AVEncMPVGOPSize)`，而且**必须在类型协商之前**写；两个坑：① `MF_MT_MAX_KEYFRAME_SPACING` 完全无效；② vtable 里 `SetValue` 是 **slot 9**（slot 8 是 `GetValue`，写错了不报错、回读到 0）。
- **不要用「每秒重建编码器」换 IDR**：NVENC 每个进程大约只能建 12–13 个 MFT 实例，之后连 `SetInputType` 都开始报 `MF_E_UNSUPPORTED_D3D_TYPE`，录制直接死。同一会话里 `COMMAND_FLUSH` / 重新 `SetInputType` 都不会再吐 IDR。

### 5.1 配额 / 保留期（2026-10-28 已实现）

| 参数 | 默认 | 说明 |
|---|---|---|
| `QuotaGb` | **40** | 库里片段总体积上限；**0 = 不限** |
| `RetainDays` | **30** | 超过就删；**0 = 永久保留**（用户 Q18 明确要能选永久或定时清理） |
| `WatermarkGb` | **2** | 磁盘可用空间低于此值 → 暂停录制；**0 = 不检查** |
| `CheckMinutes` | **60** | 定时检查间隔 |

配置来自数据目录下的 `config.json`（`--config=` 可指定），读不到或写坏了都退回默认值，**绝不因配置问题启动失败**。

清理是两条独立的删除理由，顺序固定：
1. **超期**：`CreatedLocal < now - RetainDays` 的一律删，不看体积。
2. **超配**：还超配额时按**淘汰优先级**从旧到新删到配额内。优先级 `被击倒 > 击倒 > 击杀` —— 先牺牲队友/自己被击倒的，最少删自己击杀的高光（spec 早期定下的规矩）。同优先级内按时间从旧到新。

触发点（spec §5 原定的三个）：**启动时**、**每片落盘后立即**、**每小时**。

**片段索引靠文件名，不建数据库**：`{gameId}_{MMdd-HHmmss}_{score:F2}.mp4`，可选在 gameId 后加 `_k`(击杀) / `_kd`(被击倒)，缺省是击倒。解析从**尾部**取（`parts[^2]` 时间、`parts[^1]` 分数、`parts[^3]` 种类），这样 gameId 本身含下划线也不受影响。跨年时 `MMdd` 会回到 1 月，年份补成「不晚于今天」的最近一次。

**水位语义**：跌破水位后停止往环形写入（`RecordingPaused`），但**已经录好的片段照常落盘成片**——对应不变量「磁盘写满优先于画面质量：到水位先停，不丢已经录好的」。恢复后自动续录。

**自检**：`--quota-test` 在临时目录伪造片段，验证解析、超配淘汰顺序（断言第一个被删的是 `_kd_`）、过期删除、`RetainDays=0` 永久、水位判定、配置往返与坏配置退回默认。全部断言通过才返回 0。`--lib-list` 打印库现状（旧→新，含种类/分数/体积），`--quota-run` 真跑一次清理。

### 5.5 音频轨（2026-10-28 已实现）

用户原话（Q16）：「音频肯定要录的」；范围经确认为**只录系统/游戏声**，不录麦克风、不做分离轨道。

| 环节 | 选型 | 理由 |
|---|---|---|
| 采集 | WASAPI loopback，默认渲染端点，`FlagsLoopback` | 不加驱动、不注入；事件驱动优先，不支持则退回轮询 |
| 采样格式 | 设备混音格式原样（实测 48kHz/2ch/float32，960 帧 = 20ms 一包） | 统一转 int16 交错立体声，避免重采样 |
| 编码 | `Microsoft AAC Audio Encoder MFT`，48kHz/2ch/**160kbps** | 系统自带，无需打包第三方；48kHz 是它原生支持，零重采样 |
| 时间轴 | 与视频共用同一个 `Stopwatch`，微秒级 | 两条轨必须同轴，否则切片时音画错位 |
| 缓冲 | 内存环形（不是分片文件） | 160kbps = 20KB/s，90s 才 1.8MB，比视频小两个数量级 |
| 封装 | mp4 第二条 `trak`：`hdlr=soun`、`smhd`、`stsd=mp4a`+`esds` | 单文件双轨，不用外部混流器 |

**esds / ASC 的坑（踩了半天）**：`MF_MT_USER_DATA` 对 AAC 返回的是完整的 `HEAACWAVEINFO` 去掉 WAVEFORMATEX 的部分（14 字节：12 字节固定头 + 2 字节 ASC）。
把整段 14 字节都塞进 `DecoderSpecificInfo` 会让解码器把 `0x0000` 读成 audioObjectType=0、采样率索引=0，**解出来变成 96000Hz**（音量正常但音调高一个八度）。
正确做法是取 `userData[12..]`，也就是真正的 2 字节 `{0x11,0x90}`（AAC-LC / 48kHz / 立体声）。

**验证手法**（不靠听）：
- `--av-test`：离线合成 440Hz 正弦 + 渐变画面 → 双轨 mp4，再用 `--audio-check` 解码回 PCM 量峰值。合成的 ±12000 解出来峰值 **12014**，说明 AAC 往返无损。
- `--audio-check`：把音轨解成 PCM，报峰值/RMS/有声样点数；峰值 < 500 判定为静音。**双轨存在不等于有声音**——ASC 写错时样本数一样正常。
- 实机：`--title=BenchWnd --fake-hit=12` 出片后 `--mp4-check` 显示视频 600 样本 / 音频 205 样本，末时间戳相差 **19ms**，解码峰值 11144。

**关闭开关**：`--no-audio`（整个音轨）、`--no-beep`（只关提示音）。

### 5.6 路径与分发（2026-10-28 已实现）

**问题**：此前有 14 处硬编码 `D:\played`（`Capture.cs` 的 `OutDir`/`ClipDir` 默认值、`Program.cs` 各处自检目录、`TrayApp.cs` 开库/开目录、`run-live.bat`）。换机器或别人下载就写不进文件。实测从 `C:\` 目录跑 `--lib-list` 仍报 `D:\played\captures\clips`，证明是编译期写死的。

**`Paths.cs` 是唯一来源**，数据根按顺序决定（第一个命中）：
1. 命令行 `--data=<dir>`（必须在任何路径被访问前调用）
2. exe 同目录（可写时）—— 便携式，解压即用，删目录 = 清空
3. `%LOCALAPPDATA%\ApexHighlights` —— exe 在 Program Files 之类只读位置时

可写性判定是**真的写一个 `.write_test` 文件再删**，不查 ACL（UAC 虚拟化会骗人）。

**开发态特判**：exe 路径含 `bin` 段时，向上找 `.git` 或 `games/apex.json`，命中就用源码树根作数据根 —— 开发时 `captures/` 仍落在仓库里；发布版不在 `bin` 下，不会误判。

**单文件分发**：`Properties/PublishProfiles/single-file.pubxml`（`PublishSingleFile` + `SelfContained` + `RuntimeIdentifier=win-x64` + `IncludeNativeLibrariesForSelfExtract` + `EnableCompressionInSingleFile`）。参数**刻意不写进 csproj** —— `RuntimeIdentifier` 一旦进 csproj，普通 build 也会多出 `win-x64/` 子目录，`run-live.bat` 与日常调试路径全跟着变。

**内置配置随 exe**：`<EmbeddedResource Include="..\..\games\**\*" LogicalName="games/%(RecursiveDir)%(Filename)%(Extension)" />`；`Paths.EnsureGames()` 首启释放，**已存在则跳过**（用户改过的配置不能丢）。

**实测**：`dist/ApexHighlights.exe` 70MB 单文件，单独拷到空目录后 `--gpu-test` / `--av-test` / `--audio-check` / 真实录制 / `--lib-ui` / `--tray-test` 全部通过，`[0] 数据目录` 指向该空目录，全流程无一处 `D:\played`。

**提示音**：录完一段响一声两音符（C6→G6，181ms），`winmm.PlaySound` + 内存合成的 WAV，**不弹任何窗口**（用户明确要求）。现场合成而不带音频文件，是为了挪目录也不会坏。

## 6. 不变量

1. 任何配置都不能让环形缓冲短于「最大前摇 + 后摇」。
2. 检测失败必须**静默降级**，不能打断录制。
3. 录制不能阻塞采集：编码队列深度 2–4，满了丢最旧。
4. 磁盘写满优先于画面质量：到水位先停，不丢已经录好的。
5. 不注入、不读内存、不模拟输入。

## 8. 开放问题

- 击杀与击倒是否在 v1 同时开工（当前 v1 只做「我击倒别人」）。
- 录制分辨率：原生 2560×1440 还是降到 1080p（直接影响单条体积：60s@20Mbps ≈ 150MB）。**2026-10-28 已在 2566×1454 窗口实测 60fps 零丢帧**，原生分辨率可行，但体积与默认值的取舍还需用户拍板。
- 独占全屏下的黑屏风险（WGC 依赖 DWM 合成，实测未覆盖）。
- 音频是否需要「只在录制片段期间才编码」以减少常驻 CPU（当前全程编码，实测占用可忽略，但没量过）。
- 音频环放在内存（90s ≈ 1.8MB）在长时间运行时是否要加硬上限，还是随环形一起只受 keepSeconds 约束。
